# Canonical Runtime Participant Identity and Custody Protocol

Status: **CANONICAL / NORMATIVE**  
Applies to: NutEV scientific validation rounds  
Primary scope: assessor identity, adjudicator identity, external-test custody, runtime participant configuration, private links/tokens, persistence and auditability

## 1. Purpose

This document defines the canonical architecture and governance rules for human participants in NutEV scientific validation.

Its purpose is to prevent participant identities from becoming source-code constants, repository metadata, reproducible fixtures, or hidden assumptions in the validation workflow while preserving scientific traceability, blinding, auditability and external-test custody.

This protocol is normative. If another implementation note, example, script invocation, UI label or README conflicts with this document, this document governs unless an explicit preregistration amendment states otherwise.

## 2. Core principle

**Scientific roles may be fixed by protocol. Human identities may not be fixed by code.**

NutEV may enforce semantic roles such as:

- coordinator;
- assessor;
- adjudicator;
- external-test custodian.

NutEV may enforce scientific constraints such as:

- at least two independent assessors per benchmark-grade item;
- independent blinded assessment before adjudication;
- external-test evidence remaining sealed until the validation continuation decision is locked.

NutEV must not encode a specific real person as any of those roles in source code, committed configuration, test fixtures used as production configuration, public manifests or repository documentation.

## 3. Definitions

### 3.1 Real participant identity

Any data that directly or practically identifies the human participant, including:

- name;
- email address;
- phone number;
- account username;
- institution-specific identifier;
- personal GitHub identity;
- any stable label intentionally derived from the person's identity.

### 3.2 Opaque participant ID

A non-semantic identifier used by NutEV to address one participant inside one scientific workflow without revealing who that person is.

Examples:

```text
assessor_4e93d6a2
assessor_c2a91b74
adjudicator_19a0f41e
custodian_803bb4f2
```

An opaque ID must not encode initials, name fragments, email fragments, role-holder identity or institution.

### 3.3 Round ID

A runtime identifier for one validation round, generated by the system.

Example:

```text
vr_<opaque-runtime-id>
```

### 3.4 Private participant mapping

A private operational record that maps an opaque participant ID to the real human who holds that role.

Example conceptually:

```text
opaque_id -> real person
```

This mapping is not part of the public scientific repository and must not be required to reproduce ranking metrics.

### 3.5 Reviewer token

A private runtime credential that authorizes one assessor session. It is not an identity and must never be committed to Git.

## 4. What is allowed to be fixed in code

The following are protocol/schema constants and may be represented in code when versioned and documented:

- supported role names;
- minimum assessor count required by the scientific protocol;
- allowed relevance scale (`0`, `1`, `2`);
- required columns and schemas;
- validation state-machine states;
- blinding rules;
- fail-closed rules;
- required audit events;
- cryptographic/hash algorithms used for integrity;
- artifact naming contracts;
- the scientific candidate SHA for a specific preregistered round, when it is explicitly a frozen research object.

A frozen scientific candidate SHA is **not** a hard-coded participant identity. It is an immutable research-object reference used to establish which software was tested.

## 5. What must be runtime/private

The following must not be committed as production participant configuration:

- names of assessors;
- names of adjudicators;
- names of custodians;
- emails or contact details;
- real-person-to-role assignments;
- reviewer tokens;
- external-test release credentials;
- private participant mapping;
- participant-specific access URLs;
- participant-specific session secrets.

The number of assessors must be configurable at runtime subject to the scientific minimum. The architecture must not assume exactly two assessors merely because the current preregistration requires at least two.

## 6. Repository boundary

### 6.1 Git may contain

- validation source code;
- schemas;
- canonical protocols;
- scientific preregistration;
- generic role definitions;
- non-identifying examples;
- tests using obviously synthetic IDs;
- public scientific outputs that do not expose protected participant identity;
- hashes and manifests that are scientifically necessary and safe to publish.

### 6.2 Git must not contain

- private participant mapping;
- real participant names as runtime configuration;
- real participant emails;
- reviewer tokens;
- private reviewer links;
- external-test labels before their protocol-authorized release;
- external-test gold before protocol-authorized release;
- credentials or secrets;
- private operational contact lists.

A synthetic identifier such as `assessor_A` may appear in a unit test or explanatory example only if the surrounding context makes clear that it is not a production identity. It must not be the canonical production setup instruction.

## 7. Runtime identity model

The canonical flow is:

```text
create validation round
        |
        v
generate round_id
        |
        v
set assessor_count >= scientific minimum
        |
        v
generate opaque assessor IDs
        |
        v
create private operational mapping outside Git
        |
        v
generate isolated reviewer sessions/tokens
        |
        v
perform blinded assessment
        |
        v
lock submissions
        |
        v
adjudicate conflicts
        |
        v
build/validate gold standard
        |
        v
calculate validation-only metrics
        |
        v
lock continuation decision
        |
        +---- STOP_AT_B -> external remains sealed
        |
        +---- CONTINUE_TO_EXTERNAL -> custodian may release external evidence
```

## 8. Opaque assessor ID generation

### 8.1 Requirements

Generated assessor IDs must be:

- non-empty;
- unique within the round;
- stable for the duration of the round;
- non-identifying;
- safe for filenames/database keys;
- independent of human names or contact information.

### 8.2 Count

The runtime interface must accept an assessor count or an equivalent dynamic participant definition.

Scientific constraint:

```text
assessor_count >= 2
```

This is a minimum, not a maximum.

A future round may use three or more assessors without modifying application source code.

### 8.3 Explicit IDs

An advanced/operator path may accept explicitly supplied participant IDs only when they are opaque IDs.

The system must reject blank IDs and duplicate IDs.

The canonical user-facing path should prefer system-generated opaque IDs rather than requiring operators to invent labels manually.

## 9. Real identity mapping and custody

The real-person mapping exists only to allow the coordinator to know who should receive each private session and to document human accountability when needed.

It must be stored separately from the public benchmark artifacts.

Minimum fields for a private operational registry may include:

```text
round_id
opaque_participant_id
role
real_identity
contact_route
assigned_at
mapping_owner
status
```

This registry must be treated as operational/private data.

It must not be consumed by ranking, scoring, gold-standard calculation or scientific metric computation.

Scientific reproducibility must depend on opaque IDs and immutable assessment artifacts, not on publication of assessors' private contact data.

## 10. Reviewer session and token contract

Each assessor receives an isolated session.

The session must expose only information required for independent judgment.

It must not expose:

- NutEV rank;
- baseline rank;
- system membership;
- score breakdown;
- taxonomy score;
- another assessor's decisions;
- pool audit metadata that reveals ranking/system membership.

Tokens must:

- be generated at runtime;
- be unpredictable;
- authorize only the intended reviewer session;
- never be embedded in committed source code;
- never be written to public scientific artifacts;
- be invalidated or made unusable when the protocol says the session is locked/closed.

Private reviewer URLs are operational credentials and must be handled as secrets.

## 11. Participant count and assignment rules

The scientific protocol sets minimum independence requirements; the software implements them generically.

For benchmark-grade validation:

```text
minimum independent assessors per reference >= 2
```

The software must not implement this as:

```text
person_1 = <specific human>
person_2 = <specific human>
```

It must implement the invariant:

```text
unique independent assessor IDs >= required minimum
```

Assignment strategy may evolve without changing the identity model, including:

- all assessors judge all items;
- balanced multi-assessor assignment;
- stratified assignment with guaranteed overlap;
- larger panels.

Any such change must preserve the preregistered scientific coverage requirements.

## 12. Coordinator contract

The coordinator may:

- create a round;
- choose/configure participant count;
- privately map opaque IDs to real participants;
- distribute private links;
- observe completion/progress metadata;
- start adjudication only after initial assessments are locked;
- build gold only after adjudication rules are satisfied;
- calculate validation metrics only after gold validation passes;
- lock the validation decision.

The coordinator must not be given reviewer decisions before the protocol permits them if doing so would break blinding or external-test separation.

## 13. Adjudicator contract

The adjudicator is a role, not a hard-coded person.

The adjudicator identity must be configured privately at runtime/operations level and represented inside scientific artifacts by an opaque identifier where attribution is needed.

The adjudicator should receive only the information needed to resolve conflicts after initial judgments are locked.

A script must not silently replace human adjudication by selecting a winning assessor, averaging grades, or inferring a final relevance label.

## 14. External-test custodian contract

The external-test custodian is logically separated from the analyst responsible for the validation-stage continuation decision.

Before `CONTINUE_TO_EXTERNAL` is locked, the custodian must not reveal to that analyst:

- completed external assessments;
- external gold labels;
- external performance metrics;
- system-specific external error analysis;
- information that would permit tuning the frozen candidate against external outcomes.

The custodian's real identity must not be hard-coded into the application.

External custody configuration and release authorization are runtime/private operational state.

## 15. Scientific freeze versus application configuration

Two different concepts must never be confused.

### 15.1 Scientific freeze

A preregistered candidate SHA is intentionally immutable for one benchmark round.

This is required for scientific attribution.

### 15.2 Runtime participant configuration

The people who perform the human roles are runtime participants.

They must remain configurable and non-hard-coded.

Therefore this is valid:

```text
candidate_sha = frozen for Round 01
assessor_count = runtime configurable, minimum 2
assessor IDs = generated/runtime
real participant mapping = private
```

This is invalid:

```text
candidate_sha = mutable during the same scientific round
assessor_1 = fixed real person in source code
assessor_2 = fixed real person in source code
```

## 16. Persistence model

Runtime validation state may be persisted in a local/private database or equivalent durable store.

The persisted operational state may include:

- round ID;
- opaque participant IDs;
- token/session state;
- assignment state;
- assessment completion state;
- locked judgments;
- adjudication state;
- audit events.

The persistence layer must not require committed source-code changes to add/remove participants for a new round.

A new round must be creatable without editing Python, JavaScript, JSON committed to Git, or test fixtures.

## 17. UI/API contract

The canonical product experience should allow the coordinator to prepare a round without editing source code.

At minimum, the product/runtime API must support the equivalent of:

```text
prepare round
set/generate participant count
obtain opaque participant sessions
copy/distribute private reviewer links
track completion
lock submissions
adjudicate conflicts
build gold
run validation metrics
lock continuation decision
```

The UI must not imply that exactly two named users are part of the software architecture.

Labels such as "Avaliador 1" and "Avaliador 2" are display conveniences only. They must be derived from runtime participants and must not define production identity.

## 18. Auditability requirements

For every validation round, the system should preserve an audit trail sufficient to answer:

- which round was executed;
- which scientific candidate SHA was tested;
- how many independent assessors participated;
- which opaque IDs participated;
- which assignment each opaque ID received;
- whether blinding was preserved;
- when submissions were locked;
- whether adjudication occurred and by which opaque adjudicator ID;
- when the gold standard passed validation;
- when the continuation decision was locked;
- whether and when external evidence was released.

Public scientific artifacts may use opaque IDs. The private real-identity mapping is not required to be public.

## 19. Fail-closed rules

The validation workflow must stop or refuse promotion when any of the following occurs:

- fewer than the required independent assessors are present;
- duplicate participant IDs collapse nominally independent assessors;
- a participant ID is blank;
- a private packet contains prohibited ranking/system fields;
- pre-existing judgments appear in an initial blinded packet;
- required blinding status is false/broken for evidence claimed as benchmark-grade;
- required gold-standard coverage is incomplete;
- external-test information is released before the continuation decision is locked;
- participant runtime data is missing in a way that makes scientific provenance ambiguous.

No default real person may be silently substituted to bypass a missing participant configuration.

## 20. Test contract

Regression tests must cover at least:

- runtime generation of opaque assessor IDs;
- minimum assessor count enforcement;
- support for more than two assessors;
- uniqueness of generated IDs;
- deterministic behavior where required by the packet-generation contract;
- rejection of blank/duplicate explicit IDs;
- absence of ranking/system leakage in assessor packets;
- round ID generation at runtime;
- private token generation at runtime;
- isolation of reviewer sessions;
- no source-code dependency on real participant identity;
- correct fail-closed behavior when participant requirements are not satisfied.

Tests may use synthetic labels such as `assessor_A` only as test data. Such fixtures do not define the production runtime architecture.

## 21. Prohibited implementation patterns

The following patterns are prohibited:

```python
ASSESSOR_1 = "Real Person Name"
ASSESSOR_2 = "another@email.example"
```

```javascript
const reviewers = ["person@example.com", "other@example.com"]
```

```json
{
  "production_assessor_A": "Real Name",
  "production_assessor_B": "Real Name"
}
```

Also prohibited:

- naming production branches/files after private participants for operational assignment;
- using GitHub usernames as implicit scientific participant IDs;
- deriving opaque IDs from names/emails without a privacy-preserving boundary;
- putting reviewer tokens into README examples copied from real rounds;
- treating `assessor_A` and `assessor_B` as mandatory production identifiers.

## 22. Accepted implementation patterns

Preferred:

```text
assessor_count = 2
-> system generates two opaque assessor IDs
-> coordinator privately maps each ID to a real person
-> system generates isolated reviewer tokens
```

Also acceptable for advanced automation:

```text
explicit opaque IDs supplied at runtime
-> validated as unique/non-empty/non-identifying
-> no real identity committed
```

For larger panels:

```text
assessor_count = 4
-> same code path
-> no application source change
```

## 23. Artifact publication rule

Public validation outputs may include:

- round ID;
- candidate SHA;
- opaque assessor IDs where methodologically necessary;
- aggregate agreement measures;
- final adjudicated labels;
- integrity hashes;
- audit timestamps when appropriate.

They must not require publication of:

- assessor email addresses;
- phone numbers;
- private reviewer tokens;
- private participant mapping;
- operational contact details.

If a publication requires author-level disclosure of assessors for methodological reasons, that disclosure is handled explicitly in the manuscript/ethics/reporting process, not by embedding identity in application source code.

## 24. Change control

Changes to this protocol that affect scientific independence, blinding, participant minimums, custody or external-test leakage rules require:

1. a documented rationale;
2. versioned review;
3. compatibility assessment with the current preregistration;
4. a preregistration amendment when the scientific protocol changes;
5. preservation of previous-round artifacts without retroactive rewriting.

Implementation improvements that only replace hard-coded/manual configuration with equivalent runtime configuration do not change the frozen ranking candidate, provided they do not alter the tested ranking/query/taxonomy/runtime behavior attributed to that candidate.

## 25. Definition of done

The participant-identity architecture is considered compliant only when all statements below are true:

- [ ] no real assessor identity is required in committed source code;
- [ ] no real adjudicator identity is required in committed source code;
- [ ] no real custodian identity is required in committed source code;
- [ ] assessor count is runtime configurable with a scientific minimum;
- [ ] opaque participant IDs are generated or supplied at runtime;
- [ ] a new round can use different humans without a code change;
- [ ] reviewer tokens/links are generated at runtime and remain private;
- [ ] real-person mapping is outside Git;
- [ ] external-test custody remains separated and fail-closed;
- [ ] tests prevent regression to fixed production participants;
- [ ] the Human Validation Runbook references this protocol;
- [ ] examples using A/B are clearly synthetic, not canonical production setup.

## 26. Canonical rule in one sentence

> **NutEV freezes the scientific object being tested, not the humans who test it: participant roles are protocol constraints, while participant identities, counts above the scientific minimum, assignments, session IDs and credentials are private runtime configuration.**
